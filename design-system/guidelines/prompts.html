Prompts

This system already has names for everything in it. A prompt that uses those names gets the real thing back; a prompt that describes the look gets an imitation of it. This panel is the vocabulary, the phrasings that work, and the guardrails worth pasting into every request.

Applies to Claude, to Claude Code, and to any handoff conversation about this system

01 · The one rule

Name the thing, do not describe it. Every colour, shell, effect and component here has a token or a component name. Ask for --day-sat and you get the exact Saturday green with its text pair and calm-mode behaviour. Ask for "a bright green" and you get a new green that belongs to nothing, breaks the day system, and has to be undone.

04 · Guardrails worth repeating

Paste these into any prompt that touches visual design here. They are the failures that actually happen.

No new colours

Every colour is a token. If a request seems to need a new one, that is a signal the wrong token is being used, not that the palette is short.

One neon per element

An element gets one accent. Two neons on one object reads as a bug, not as energy.

No em dashes

Not in any copy: UI labels, blurbs, button text, docs. Use a period, comma, colon, parentheses, or "to" for ranges.

Calm mode is not optional

Any bloom, blur, pulse or glitch needs its calm branch in the same change, or the accessibility switch silently stops working.

Live product is truth

When the guide and the running site disagree, the site wins and the guide gets fixed. Say which one you read.

Compose, do not re-draw

Reach for the shell, the atoms and the button classes. A hand-rolled stack that looks right today drifts by the next change.

05 · Two different asks

Be explicit about which one you are making, because the right answer is opposite in each case.

Using the system

"Build a Housing board card." The answer is the existing shell at a different accent, and nothing new. If it needs something new, that is a red flag to raise, not a licence to invent.

Changing the system

"The claim sticker should not be magenta anymore." The answer touches the token layer, the panel that documents it, and every surface that inherits it. Say "this is a change to the system" out loud so all three get updated together.

The stale-guide trap

This guide has been wrong before, in ways that read as authoritative: a 3px category top border that was never in the code, a magenta claim sticker that had been retired, a 2px seam that renders at 1.5px. A prompt that says "follow the guide" inherits those errors.

Ask for the fact-check as part of the work: read the live component, tell me where this panel contradicts it, fix both.

06 · Handing the whole thing over

To rebuild or extend this system elsewhere, do not paraphrase it. Send the artifacts: the token files, the panel that documents the area, and the live component. The Read me panel has a Copy the rules block button that puts the full written standard on the clipboard, which is the fastest correct opener for a fresh conversation.

  1. Paste the rules block first, before any request.
  2. Name the panel and the token file the work touches.
  3. State whether this is using the system or changing it.
  4. Ask for the drift list before the code.
